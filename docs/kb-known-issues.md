# 지식베이스 Known Issues

2026-09-15 최종 적재 시점 기준. 적재 파이프라인은
`kb_extract.py` → `kb_analyze.py` → `kb_load.py` 순서다.

방침: **잘못된 관계가 그래프에 들어가는 것보다, 일부 관계가 빠지는 쪽을 택한다.**
아래 항목들은 전부 "정보를 잃더라도 막는다"는 결정의 결과다.

---

## 1. `PROCEDURE → REQUIRES → DOCUMENT` 가 `DOCUMENT → REQUIRES → DOCUMENT` 로 추출됨

**상태**: 차단 중 (27건 폐기). 고치지 않고 둔다.

제출서류 목록 문단에서 모델이 절차를 빼먹고, 그 절차의 *결과물*인 서류를
주어로 삼는다.

```
외국인등록증 -[REQUIRES]-> 여권          근거: "재발급시 제출서류 - 여권"
외국인등록증 -[REQUIRES]-> 통합신청서      근거: "통합신청서 1부"
외국인등록사항변경신고서 -[REQUIRES]-> 여권  근거: "여권 및 외국인등록증"
```

올바른 형태는 `외국인등록증 재발급 -[REQUIRES]-> 여권` 이다.
`10_하이코리아_외국인등록증_재발급.pdf` 청크에는 PROCEDURE 엔티티가 아예
생성되지 않았다.

**왜 타입 표를 열지 않는가**: 열면 "외국인등록증" 노드가 *카드 자체*와
*카드 발급 절차* 두 의미를 겸하게 된다. "재발급에 뭐가 필요해?" 같은 질문의
그래프 탐색 경로가 오염된다.

**고치려면**: 프롬프트에 "제출서류 목록의 주어는 서류가 아니라 절차다"를
넣고 해당 6개 문서의 청크만 재추출한다. 캐시가 있으므로 전체 147청크를
다시 부르지 않는다.

```
docker compose exec -T -e LLM_PROVIDER=openai -e ONLY=<chunk_id,...> \
    backend python - < scripts/kb_extract.py
```

영향 문서: `07_동아대_국제교류과_VISA정보`(6), `10_외국인등록증_재발급`(6),
`11_외국인등록사항_변경신고`(5), `13_전자민원목록`(1), `14_비자포털_절차`(8),
`32_모바일외국인등록증_계좌개설`(1)

## 2. PDF 메타데이터 줄에서 가짜 관계가 만들어짐

**상태**: `PRODUCT → ISSUED_BY → ORGANIZATION` 조합을 막아 차단 중 (6건).
predicate 를 새로 만들지 않는다.

문서 하단의 출처 표기를 모델이 관계로 읽는다.

```
학부 영어트랙 장학금 -[ISSUED_BY]-> 동아대학교 국제교류과   근거: "출처기관: 동아대학교 국제교류과"
외국인주민지원 -[ISSUED_BY]-> 부산광역시                근거: "출처기관: 부산광역시"
```

6건 중 실제 관계는 `모바일 신분증 공통 기반 -[ISSUED_BY]-> 행정안전부`
하나뿐이다. 1건 때문에 predicate 를 늘릴 이유가 없다.

**향후 개선(ingestion)**: `cleaner.clean_text()` 에서 `출처기관:`, `출처:`,
`수집일:`, `확인/수정일:`, `카테고리:`, `URL:` 로 시작하는 메타데이터 줄을
제거한다. 근본 원인이 여기다. 이 줄들은 검색에도 도움이 되지 않는다.

## 3. 엔티티 타입 오분류 — PRODUCT 와 DOCUMENT/CONDITION

**상태**: 일부만 차단. 전부 막지는 않는다.

모델이 애매한 것을 PRODUCT 로 밀어 넣는 경향이 있다. `체납액`(금액),
`시간제 아르바이트`(활동) 등. `validation._PRODUCT_NOISE_RE` 가 교통편·금액·
번호 같은 명백한 것만 잡는다 — 과도한 하드코딩을 피하기 위한 선택이라
`체납액` 처럼 새는 것이 있다.

이 오분류로 만들어진 관계는 type×predicate 검사에서 걸러진다.

## 4. 타입 불일치로 폐기되는 관계 216건

**상태**: 의도된 차단. 대부분 사실관계가 틀렸다.

```
22건  VISA -[APPLIES_TO]-> DOCUMENT          문화예술(D-1) → 각 체류자격별 제출서류  (REQUIRES 여야 함)
20건  ORGANIZATION -[SUBMITTED_TO]-> ORGANIZATION  징세기관 → 법무부
13건  ORGANIZATION -[ISSUED_BY]-> ORGANIZATION     한림생활관 → 동아대학교 (소속이지 발급 아님)
10건  ORGANIZATION -[SUBMITTED_TO]-> CONDITION     부산청 종합민원센터 → 부산광역시 (관할구역)
```

`ORGANIZATION → ORGANIZATION` 은 실제 제출 대상이 기관이 아니라 '체납정보'
같은 다른 개념인 경우다. 타입 조합을 넓혀 통과시키지 않고 endpoint 추출
오류로 처리한다.

## 5. 관계 없는 ORGANIZATION 은 그래프 노드로 만들지 않음

**상태**: 의도된 정책 (`validation.DROP_UNUSED_ORG_IN_DESCRIPTIVE`).

설명성·목록 문단에서 나왔고 채택 관계에 한 번도 참여하지 않는 기관은
그래프에 넣지 않는다. 147청크 감사 결과:

- 고유 기관 312개 중 264개(85%)가 관계에 미참여
- 그중 237개는 설명성·목록 문단 전용이고, **98%가 청크 본문에 그대로 있음**
- ORGANIZATION 생성량의 77.5%가 `listing` 문단
- 네 문서(소속기관·기관소개·1345안내센터·오시는 길)가 1,133개를 생성
  — 전국 검찰청 목록이 대표적이다

검색에 필요한 것은 '이름이 본문에 있다'이지 '그래프에 노드가 있다'가 아니다.
이름은 Chunk 본문과 임베딩으로 닿는다. **관계를 가진 기관은 어느 문단에서
나왔든 그대로 남는다.**

되돌리려면 `DROP_UNUSED_ORG_IN_DESCRIPTIVE = False` 로 두고 `kb_analyze.py`
와 `kb_load.py` 를 다시 돌린다 (API 호출 없음).

## 6. 최종 적재는 규칙 기반 추출기를 타지 않음

**상태**: 의도된 선택. 기록해 둔다.

`kb_load.py` 는 `validated.jsonl` 에 있는 것만 넣는다. 기존 인제스트 경로가
함께 돌리던 `RuleExtractor`(비자코드 정규식 + 기관명 8개, 약 331건)는 포함되지
않는다. 분석에서 확인한 숫자와 적재 결과가 어긋나지 않게 하기 위해서다.

LLM 이 VISA 엔티티를 200개 이상 뽑고 있어 실질 손실은 크지 않을 것으로
보지만, 검증하지는 않았다.

## 7. 30자 이름 제한이 만들던 연쇄 유실 — 해결됨

**상태**: 해결. 이력으로 남긴다.

엔티티 이름이 30자를 넘으면 무조건 잘랐고, 그 이름을 쓰던 관계가 endpoint
누락으로 함께 사라졌다. `International Student Academic Excellence
Scholarships A, B, C, D` 같은 정상 제도명이 대상이었다.

상한을 75자로 올리고 문장 판별을 따로 뒀다 (`_looks_like_sentence`):
75자 초과 / 한글 어절 9개 이상 / 영어 기능어 3개 이상 / 영어 소문자 시작.
실사례 24건 검증에서 고유명사는 통과하고 문장은 차단됐다.
endpoint 누락 64건 → 51건.
